# Baton — 規模化的注意力

[English](ATTENTION.md) · **繁體中文**

一支隊伍大多時候都是好好的。四十五個面板正照著你交代的事在跑,而你會盯著螢幕,是為了另外那五個。到了這個規模,你就
不是一個照著清單做事的操作員了——你是一個**例外處理器(exception handler)**,而唯一值得回答的問題只有一個:

> **隊伍什麼時候需要一個人?而那個人要怎麼把待辦清空?**

這一頁上的每一件事,不是這個問題的前半,就是後半。找出想找你的面板從來不是難的部分;頁尾那個徽章早就知道數字了。
真正的成本是**清掉**它們——而一份你清不完的待辦,是一份你會不再相信的待辦,那比沒有待辦更糟。

## `idle` 是三件不同的事戴著同一個徽章

在這之前,任何安靜下來的東西都變成 `idle`,而 `idle` 蓋掉了三個毫不相干的事件:

| 實際發生了什麼                   | Baton 說 |
| -------------------------------- | -------- |
| agent 做完了它這一輪,在等你      | `idle`   |
| agent 一直在跑,已經十分鐘沒聲音  | `idle`   |
| 一個從星期二以來沒人碰過的 shell | `idle`   |

第一列的差別 Baton 本來就知道——面板身上記著它是 **agent** 還是 **shell**——卻從來沒說出口。所以現在它說了:
**安靜的 agent 意思是「做完了,來看一下」;安靜的 shell 意思是「沒人在打字」。** 沒有新的啟發式判斷,也沒有新的
偵測風險,只是把隊伍早就知道的事講出來。第二列則是以前用任何方式都看不見的,它拿到了自己的狀態。

## 一支安靜時鐘

`running` 之上的每一道門檻都讀**同一個**數字:距離這個面板最後一個輸出位元組過了多久。不是目前狀態維持了多久——
那樣會在每一階都把梯子歸零,讓面板永遠卡在 `done`;而重點正是,一個在一分鐘處落到 `done` 的面板,必須能在中間沒有
任何一個位元組的情況下,繼續爬到十分鐘的 `stuck`。

```txt
   安靜時鐘 —— 距離這個面板最後一個輸出位元組的時間
   ├──────────────┬──────────────────┬───────────────────────────────>
   0             10s                60s                             10m
                  │                  │                                │
 ┌──────────┐     ▼    ┌──────────┐  ▼   ┌──────────┐     ┌──────────┐
 │ running  │ ───────> │   idle   │ ───> │   done   │ ──> │  stuck   │
 └────▲─────┘          └──────────┘      └──────────┘     └──────────┘
      │                 shell 停            來看一下        安靜得太久了
      │                 在這裡                                       │
      │                                     只有 agent ──────────────┘
      │
      └──── 一個輸出位元組就把任何一階帶回 running ───────────────────┘

              ┌──────────────┐      由 agent 自己舉手,或由一段長得像
              │  attention   │ ◀──  問句的尾巴引發。它壓過上面整座梯子。
              └──────────────┘
```

- **`idle`** 在 10 秒。它不可設定,而且是刻意的:它的意思是「輸出停了」,那是關於位元組串流的事實,不是對 agent 的
  判斷。
- **`done`** 在 `panel.done-after`(預設 **60s**),只有 agent 會到。它刻意是 `idle` 的六倍——一個等著單一工具
  呼叫的 agent,安靜十秒是家常便飯,把那叫做「做完了,來看一下」會讓待辦塞滿還在跑的工作。
- **`stuck`** 在 `panel.stuck-after`(預設 **10m**),同樣只有 agent 會到。它對「為什麼」隻字不提;它只說這份沉默
  已經超出了為那個 agent 設定的預算。

`done` 與 `stuck` 只給 agent,而這個排除正是整個區分的重點。一個從星期二以來沒人碰過的 shell 是刻意停在 `idle`
的:它不是在等人審閱,也沒有卡住,而每十分鐘把四十五個這種面板推上來,正是這份待辦要防的雜訊。當 shell 自己的輸出
問了問題,它仍然會到 `attention`。

**`failed` 不是一個狀態。** 一個結束得不好的面板,是帶著**非零退出碼**的 `exited`,而座艙把它畫成 failed。
常駐程式一直都把那個碼寫進 log;現在它上了線路,所以「這幾個裡面哪個掛了」變成前端能回答、而不必推論的問題。把它
留成一種**畫法**而不是一個狀態,意味著同一件事實在各處只有一種寫法。

## 一個狀態是怎麼決定的

有三樣東西可以宣稱一個安靜的面板,而它們的可信度並不相等。高的贏:

| 優先序 | 來源                                                | 可靠度 | 適用於                  |
| ------ | --------------------------------------------------- | ------ | ----------------------- |
| **1**  | agent 自己**宣告**——`baton ctl attention --why "…"` | 確定   | 任何知道 Baton 的東西   |
| **2**  | **計時器**——安靜滿 `stuck-after`,或一項任務完成了   | 確定   | 每一樣東西              |
| **3**  | **尾巴啟發式**——最後一行讀起來像個問句              | 猜的   | 任何沒聽過 Baton 的 CLI |

其中有兩個排序是承重的、而不是順手排的,而且都出自同一條原則——確定的訊號勝過猜測,能回答的項目勝過只能審閱的項目:

- **`stuck` 計時器勝過尾巴啟發式。** 一個安靜了十分鐘、而捲動內容剛好以 `?` 結尾的 agent,說它卡住比說它在等你更
  貼切。計時器是事實;尾巴是對文字的猜測。
- **尾巴啟發式勝過 `done` 計時器。** 一段在二十秒處寫著 `Apply this refactor? [y/N]` 的尾巴,是**現在**就在問的
  問題。要它等滿 `done-after` 才被叫做 `done`,等於把一個按一下就能回答的東西,埋在一個你得走過去讀的東西底下。

同一條邏輯讓「任務完成」這個事件無法把一個已經在 `attention` 的面板降級:一次派工可以在尾巴舉手的同一個 tick 裡
結算,而讓事件贏,等於在舉手後一個 tick 就把「回答我」變成「審閱我」。

## agent 可以自己舉手

計時器與啟發式都是 Baton 從外面猜。真正**知道**自己被卡住的那個參與者是 agent,而它現在有了說出口的話:

```sh
# 在 agent 面板裡:卡在一個決定上,用人類會讀到的那句話說出來。
baton ctl attention --why "two migrations conflict — which one wins?"

# ……拿到答案之後,把手放下。
baton ctl resolve
```

兩者都不用帶 id:面板自己的 id 早就在連線上了,因為 Baton 會把 `BATON_PANEL_ID` 注入**每一個 agent 面板**,不只
是 conductor。所以一個 agent 不必先搞清楚自己是哪個面板就能舉手,而這件事對整支隊伍成立,不是只對一個特權面板成
立。Shell 面板刻意被排除在外——shell 是一個啟動器,人在裡面跑的每個程式都會繼承那個標記,而坐在它前面的人早就有座艙
與 `--id` 了。

`baton_attention` / `baton_resolve` 是同一對動詞的 MCP 工具形式。`--why` 由旗標解析器與伺服器雙重要求:一份宣告
之所以能取代兩個猜測,正因為它說得出理由,而說不出理由的宣告並不比計時器值錢。理由會在進來的那一刻被清洗並截斷,
**只做一次**,所以下游每一個畫面拿到的都是已經安全的文字。完整合約——包括 `resolve` 靜音了什麼、以及為什麼
conductor 可以舉自己的手卻不能舉別人的——見 **[CONTROL.zh-TW.md § 舉手](CONTROL.zh-TW.md#舉手)**。

## 收件匣 —— `C-t a`

待辦有了一個可以被清掉的地方。`C-t a` 從**任何**畫面都能打開它,它是一個主從式(master-detail)覆蓋層:左邊是
待辦,右邊是**Monitor 當初嗅到的那同一段尾巴視窗**——一次只拉一列,永遠不搭在快照上,所以你讀到的,就是當初做出
判斷的那些位元組。

```text
╭──────────────────────────────────────────────────────────────────────────╮
│ I N B O X   1 of 3                                                       │
│                                                                          │
│ ▸ ◆ refactor-api           4m │ ▸ two migrations conflict — which wins?   │
│   ◈ migrate-db            11m │                                           │
│   ◇ docs-sweep            26m │ Files to change: internal/server/server.go│
│                               │ Apply this refactor? [y/N]                │
│                                                                          │
│ j/k move  ·  enter zoom  ·  r re-sort  ·  esc close                      │
│ i reply  ·  - snooze  ·  x dismiss                                       │
╰──────────────────────────────────────────────────────────────────────────╯
```

那個 LED 就是狀態自己的符號——`◆` attention、`◈` stuck、`◇` done、`○` 已結束——而那個時間就是安靜時鐘。當 agent 是
自己宣告需求時,它的**理由**會是尾巴窗格最上方那一行 `▸`,用的是它自己的字。尾巴本身則靠下對齊,因為那個問題永遠
是一支程式印出的最後一樣東西。

| 按鍵                 | 作用                                               |
| -------------------- | -------------------------------------------------- |
| `j` / `k`、`↓` / `↑` | 移動游標                                           |
| `g` / `G`            | 第一列 / 最後一列                                  |
| **`i`**              | **就地回覆**——那一行送進面板,該列清掉,游標留在原處 |
| `enter`              | 放大該面板——而且**什麼都不確認**                   |
| `-`                  | 把該列延後 `settings.inbox-snooze` 那麼久          |
| `x`                  | 把該列撤掉,直到該面板下次產生輸出                  |
| `r`                  | 重新排序待辦                                       |
| `esc` / `q`          | 關閉                                               |

**`i` 才是這個功能的重點。** 處理一個項目以前的成本是「導覽、enter、讀、打字、`C-t d`」——一次完整的畫面交換,還
把整支隊伍從視野裡弄丟——而連續二十次這樣的操作,才是真正的瓶頸。`i` 在覆蓋層裡打開一個小小的輸入列,用常駐程式
自己的送出方式(換行)把那一行送出去,並在同一口氣裡確認掉該列(**回覆本身就是確認**),然後把游標留在原本的索引
上——所以佇列在游標底下縮短時,下一個項目已經就位。空白的回覆會刻意送出一個純換行:接受 `[y/N]` 的預設值是一個
真正的答案,拒絕它會讓最常見的那種確認,變成這份待辦唯一處理不了的情況。

輸入列打開時,它獨佔鍵盤,所以一則含有字母 `x` 的回覆是文字而不是動詞。這裡**沒有回音**——收件匣從不 attach,
因為為每一列 attach 都要付一次重播沖刷與一次重繪,而那正是這個功能存在要消除的成本。想親眼看回覆落地的人,
`enter` 就能放大。

### 順序就是功能

列會先依**分組**、再依**最舊優先**排序,同分時以面板 id 的數值決勝,所以每一個座艙畫出來的待辦都一樣:

| 分組          | 為什麼在這個位置                                     |
| ------------- | ---------------------------------------------------- |
| 1 `attention` | 唯一一個你能在這裡**用打字**清掉的分組               |
| 2 `stuck`     | 它本來該結束卻沒有——看一眼就能處理                   |
| 3 failed      | 一個已成定局的硬事實:分流,而不是搶救                 |
| 4 `done`      | 「來看一下」,而且只在 `settings.inbox-done` 說可以時 |

「回答我」永遠不會被埋在「審閱我」底下。conductor 與 global shell 根本不會出現:它們是基礎設施、永遠都在,而一份
永遠有兩列地板的待辦,是一份沒有人清得完的待辦。

**而且只要游標還在裡面,順序就凍結。** 它只在打開時與按 `r` 時重排,其餘時候都不重排。一份抵達的快照可以改變某一列
_說了什麼_,可以在尾端追加一個新的合格者(那裡跳不過選取),也可以把一列不再合格的列變灰——但它絕不會把一列從那隻
正要動作的手底下抽走。一份會在你手下重排的待辦,是一份你按 `x` 的東西跟你讀到的東西不是同一個的待辦。

### 沒有東西會意外離開,也沒有東西會意外回來

一列 `done` 只在按 **`x` 或 `i`** 時離開待辦,別無他途——打開那個面板、放大進去再回來,它仍然原封不動地留在那裡。
一份你光是看就會消耗掉的待辦,是一份你會不再相信的待辦。

延後與撤掉是**伺服器上的隊伍狀態**,不是座艙狀態。第二個座艙把第一個剛清掉的工作再端出來一次,只是換條路走到同樣
那份不可信的待辦;而在 `--remote` 之下重新接上是夠日常的事,日常到「重連就丟掉一下午的分流成果」會變成每天的成本。
這件事的代價值得直說:兩個座艙共用同一份已清空的待辦,因此兩個人也是。

一次**撤掉**會持續到該面板**再次產生輸出**為止——而不是到它的狀態改變為止。一個被撤掉的 `done`,十分鐘後因為一個
人類完全沒有促成的計時器又以 `stuck` 回來,正是 `x` 要防的那種復活。一次**延後**是由你的座艙用你自己的設定算出來
的絕對時刻再送出去,所以兩個設定不同的座艙各自拿到各自設定的結果。兩者都不持久化:常駐程式重啟後,面板是以惰性的
已結束槽位回來的,而為那樣的面板壓下一列,等於為一個在同樣意義上已不存在的面板壓下一列。

## 儀表板告訴你工作在哪裡,而不搬動它

在儀表板上凸顯「需要人」最直覺的做法是照它排序,而那正是這裡刻意不做的一件事。卡片因為你沒造成的理由在游標底下
移動,和凍結收件匣順序要避免的是同一種迷失方向——而且在這裡更糟,因為儀表板正是它發生時你正在看的那面畫面。所以
樹保持它的形狀,改成被**標註**。

**需求計數。** 群組標題帶著 `◆N`:它有多少成員此刻會被收件匣排進待辦。這用的是待辦自己的判斷函式,是**呼叫**它而
不是重寫一份,因為兩份「需要你」的定義,等於標題宣稱兩個面板在等、而 `C-t a` 只給你一個,然後留你自己去推敲
Baton 哪一面畫面在說謊。巢狀群組會把整棵子樹摺進計數裡——一個在兩層之下求助的面板,仍然是頂層項目裡的工作。

**安靜摺疊。** 超過 `settings.fold-quiet`(預設 **8**,`0` 表示永不摺疊)之後,什麼都沒在說的面板會塌縮成一列
`▸ 12 quiet`。安靜的意思是 `idle`,或**乾淨地**結束——這兩個狀態說的是「什麼都沒發生,而且也不會發生」。非零的
退出**不**算安靜:那是一個擺在那裡等人讀的失敗。

是**摺疊,而不是丟掉**。那一列會就地展開,面板們原封不動地回到原位,因為一個會默默停止顯示面板的儀表板,是一個你
得一直拿 `baton ctl list` 去對帳的儀表板,那時它的代價已經超過它省下的了。它也坐在它吞掉的**第一個**面板的位置
上、而不是被推到最後,所以它上面那張卡與下面那張卡,還是剛才的那兩張卡。

有四樣東西永遠不會被摺,而這四樣都是你已經表態「這個重要」:**最愛**、**釘選**、**已標記**的面板,以及**游標底下**
那張卡。最後一個要是被摺了,那是 bug 而不是偏好。

那一列除了開合自己以外不擁有任何動詞——`w`、`s`、`g`、`r` 與 `*` 都會被拒絕,並在狀態列上給出正確的走法;而且它
一個 panel id 都不回答,所以一個忘了問的批次動詞會作用在「沒有東西」上,而不是一次作用在每一個安靜的面板上。有件
而且摺疊刻意對「要畫卡片還是樹狀」沒有發言權:那個計數算的是頂層**裝了什麼**,所以一個摺疊列背後的 45 個面板
就算 45 個——不論它是開、是關、還是根本沒觸發。否則光是 zoom 進某個面板(它就不再可摺疊了)再回來,整個儀表板
就會換一個樣子。

## 摘要磚摺的是長得像大家的,不是最晚來的

群組分割畫面會顯示幾張即時磚,其餘摺進摘要。它以前摺的是碰巧最晚產生的那些,而那對「誰值得看」什麼都沒說。有了
`settings.fold-similar`(預設**開**),它改成摺掉與**多數**相符的成員,把即時磚花在**離群者**身上——所以在對一個
五十個 shell 的群組廣播一次之後,答案變成「**48 個一模一樣**,2 個不同,而這就是那 2 個」。

誰跟誰像是**常駐程式**的判斷、不是座艙的,因為座艙對一個它從未 attach 過的面板一個位元組都沒有:那是面板的狀態
加上它最後一行輸出的形狀,escape 序列被剝掉(shell 幾乎在每個提示字元前都會寫一次視窗標題),數字串被摺成 `#`
(這樣進度計數器就不算差異),再雜湊成八個十六進位字元。

對於四種它沒什麼話好說的群組,這個摺疊會**婉拒**,由位置式分割接手:沒有兩個像的(一個什麼都不同的群組,絕不能把
全部都摺掉)、全部都像的、長得像的那些全被釘選了,以及一整隊各自停在轉輪不同影格上的 agent。去猜哪些字符算「同一
個動畫」會摺掉真的在做不同事情的面板,所以它不猜。

**釘選在這裡不具排他性**,而這是與位置式摺疊刻意的差別。在這個摺疊下,被釘選的成員一定是磚、而且優先吃掉配額,但
離群者仍然拿得到剩下的磚。釘選的意思是「永遠給我看這個」;把它讀成「**只**給我看這個」,會讓五十個成員裡的一個
釘選,悄悄壓掉這個摺疊存在要凸顯的每一個離群者。

一個成員數在可見磚數以內的群組根本不會摺,所以一支五個面板的隊伍完全不受這一切影響。

## 觸達一個沒在看的人

升級路徑以前止步於鈴聲,而鈴聲只傳得到常駐程式終端機所在的那張桌子。自從 `--remote` 落地之後,那張桌子往往不是你
在的那張,所以面對五十個在等的 agent,Baton 能做的最大聲的事,是在一個沒人的房間裡搖鈴。

`settings.notify` 會寫出一則 **OSC 9** 桌面通知——理由與當初替剪貼簿選 OSC 52 的完全相同。它是送給終端機的位元組,
所以不需要輔助執行檔、不需要 `notify-send`、不需要每個平台一套啟動器,而且免費跨過那一跳 ssh,因為渲染它的那台終端
機,就是坐在那個人面前的那一台。

**它會被合併(coalesce),而且這不是選配。** 隊伍規模下的失效模式不是漏掉一則警報,而是四十則同時抵達、教會某個人
把整個管道靜音。所以第一個上升緣**不會**發出:它打開一扇窗(`settings.notify-coalesce`,預設 30s),窗關上時才送
出一則通知。十二個 agent 同時走完一步,得到的是「**12 agents need you**」,而不是十二則通知。只有一個時會指名;
好幾個時只報數字,因為好幾個時沒有什麼有用的話好說。

**`done` 永遠不會發通知**,不管 `inbox-done` 開不開。凌晨兩點把人吵醒只為了說某個 agent 成功了,正是一個通知管道
被永久關掉的方式,而它會把那些卡死與失敗一起拖下水。會發通知的是 `attention`、`stuck`,以及一次**非零**退出碼的
結束——人不在的時候,他會想知道有 agent 卡住或死了,因為他不會回來讀那個說明這件事的徽章。

**它預設是關的**,與鈴聲不同,而關的意思是**一個位元組都不寫**。你 attach 上去的終端機是你自己選擇待的地方;桌面
通知則是不管你在哪裡都會找上你,而那不是軟體可以擅自假定自己受歡迎的事。鈴聲維持原樣、而且獨立:兩者觸達的是不同
的人——一個在這張桌子、一個在另一張——因為其中一個響了就壓掉另一個,等於正好在它最要緊的時候悄悄關掉升級路徑。

## 設定

這一頁上每一個判斷都是一個旋鈕,因為每一個都是對別人隊伍的猜測。預設值是那個有立場的答案;設定檔存在,就是為了跟
它唱反調。

```yaml
# $HOME/.baton/config
settings:
  # --- 注意力待辦 ---
  inbox-done: true # 做完的 agent 會進待辦;false = 只有 waiting / failed / stuck
  inbox-snooze: 10m # `-` 把一列延後多久
  notify: false # OSC 9 桌面通知,不主動要就不開
  notify-coalesce: 30s # 一扇窗一則通知,絕不是一個面板一則

  # --- 儀表板 ---
  fold-quiet: 8 # 安靜面板超過這麼多就摺成一列(0 = 永不摺疊)
  fold-similar: true # 摘要磚依相似度摺疊,而不是依位置

  bell: true # 維持原樣,且與 notify 互相獨立:進入 attention 時響鈴

panel:
  # --- 安靜梯 ---
  done-on-quiet: true # 安靜的 AGENT 面板解析成 `done` 而不是 `idle`
  done-after: 60s # ……在這麼久的沉默之後(0 = 永不)
  stuck-after: 10m # 安靜這麼久就升起 `stuck`(0 = 永不)
  agents:
    claude:
      stuck-after: 30m # 這個 profile 本來就會想比較久
```

| 鍵                         | 預設    | 含義                                                 |
| -------------------------- | ------- | ---------------------------------------------------- |
| `settings.inbox-done`      | `true`  | 做完的 agent 在收件匣得到一列「來看一下」,並計入 `◆` |
| `settings.inbox-snooze`    | `10m`   | `-` 把一列延後多久;由座艙套用,不是常駐程式           |
| `settings.notify`          | `false` | OSC 9 桌面通知                                       |
| `settings.notify-coalesce` | `30s`   | 上升緣被合併成一則通知的那扇窗                       |
| `settings.fold-quiet`      | `8`     | 安靜面板超過這麼多就摺成一列;`0` 表示永不摺疊        |
| `settings.fold-similar`    | `true`  | 摘要磚摺長得像的,而不是最晚來的                      |
| `panel.done-on-quiet`      | `true`  | 安靜的 agent 到底要不要爬到 `done`                   |
| `panel.done-after`         | `60s`   | 讓它這一輪讀起來算結束的沉默長度;`0` = 永不          |
| `panel.stuck-after`        | `10m`   | 讓沉默讀起來算有問題的長度;`0` = 永不                |

**缺席**的鍵是繼承;明確寫下的 **`0`** 是把那一階關掉。這是兩種不同的陳述,所以它們的寫法不同:`stuck-after: 0`
正是一支全是 shell 的隊伍該有的設定,而它必須撐過座艙在下一次切換設定時重寫設定檔。一個 Baton 讀不懂的門檻會被
回報並**丟棄**,於是它退回繼承,而不是默默把面板升進一個你沒要求的狀態;一座階序顛倒的梯子(`stuck` 等於或低於
`done`)會被停用較高的那一階,而不是被默默重排。

整個 `panel` 區塊都可以熱重載——`C-t R`,或給常駐程式一個 `SIGHUP`——而且門檻是**每個 tick** 從各面板的 profile
重新解析的,不是在產生時凍結的,所以一次重載可以在隊伍運行中生效,不必碰任何一個活著的面板。

### `done-on-quiet` 為什麼存在

`done` 是讓待辦**清得完**的那一階。少了它,收件匣裡只剩問題、失敗與卡死,那是一個比「這裡是所有想找人的東西,而
這裡是你把它們了結的方式」嚴格更小的承諾。這就是它預設為開的原因。

但它是為了**隊伍**這個情境預設為開的,而隊伍情境不是每個人的情境。只跑一個 agent 的人本來就在看著它:他看見那一輪
結束、他正盯著它結束的那面畫面,而替一個他看得見的狀態再加一個徽章,是**雜訊而不是訊號**。把它關掉,安靜的 agent
就停在 `idle`,和這座梯子存在之前一模一樣:

```yaml
panel:
  done-on-quiet: false # 這一個我盯著;不用告訴我它停了
```

它同時也是群組標題 `◆N` 所計的那個旗標,所以關掉它會讓兩面畫面朝同一個方向收窄——而這正是重點。兩者永遠不會互相
矛盾。

### `stuck-after` 為什麼可以逐 profile 覆寫

「安靜到久得不對勁」的正確值,**是 agent 的性質,而不是 Baton 的性質**。一支每秒印一行的 shell 腳本,停三十秒就是
卡住了。一個在規劃重構的模型,安靜十分鐘是理所當然,而一個在跑完整測試套件的則是三十分鐘。Baton 沒辦法從位元組串流
分辨這些,而且猜錯在**兩個方向**上都很貴:設得太低,每個在思考的 agent 都在喊狼來了,直到待辦被無視;設得太高,
一個真的卡死的 agent 就在那裡坐上一整個下午沒人發現。

對一支跑著不只一種 agent 的隊伍來說,沒有哪個單一數字是對的——所以就不要單一數字。它的層疊方式與
[資源上限](LIMITS.zh-TW.md)、[重啟策略](RESTART.zh-TW.md)完全一致:全隊的值是地板,而一個 profile 只重述
**它要改的那一行**。

```yaml
panel:
  stuck-after: 10m # 全隊的假設
  agents:
    claude:
      stuck-after: 30m # ……但這一個想得比較久,而那不是毛病
    lint-loop:
      stuck-after: 45s # ……而這一個停一分鐘就是卡住了
```

`done-after` 與 `done-on-quiet` 可以用同樣的方式覆寫,理由相同。

## 它不是什麼

- **不是一個會重排的儀表板。** 樹保持你安排的形狀;需求是標註在它上面的東西,絕不是對它的重新排序。
- **不是替你自動回答。** 收件匣讓回覆變便宜;它從不決定那個回覆是什麼。
- **不是花費邊界。** 這裡——以及 Baton 裡的任何地方——都沒有東西限制一個 agent 用掉多少 token。見
  **[LIMITS.zh-TW.md](LIMITS.zh-TW.md#它是什麼不是什麼)** 的說明。
- **不是持久化的分流結果。** 延後與撤掉都是對活著的行程所抱持的即時看法;常駐程式重啟會把它們清掉,因為它們所指的
  那些面板,在同樣的意義上已經不存在了。
