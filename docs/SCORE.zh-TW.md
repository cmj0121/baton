# Baton — Score

[English](SCORE.md) · **繁體中文**

> Score 是整隊的記憶。Agent 交出一則則關於「這支隊伍怎麼做事」的短觀察;一直回來的那些會沿著三階的階梯往上爬;
> 排名最高的少數幾則,會被前置到隊伍派送給每一個面板的簡報裡。它就是那個讓整隊不再重犯同一個錯的東西。

三種載體,三個擁有者。`CLAUDE.md` 屬於 repository,說的是這份程式碼怎麼寫。`CONDUCTOR.md` 屬於你,說的是
conductor 的常設命令。Score 屬於隊伍,說的是這支隊伍怎麼做事——而且三者之中,只有它會自己長大。手寫的檔案
是宣告;Score 是證據。

它預設是開的。如果你升級了一支正在跑的隊伍,然後在 agent 的終端機裡看到一個你沒有放進去的 `── Score ──`
區塊,這份文件講的就是那個東西。

## 你的 agent 終端機裡的那個區塊

每一份送到面板的簡報,前面都會接上工作集——隊伍記得的東西裡排名最高的那少數幾則,而且是針對那個面板排的:

```txt
── Score ──
- the agent was asked to gain permission it already had [noted]
- run the linter before claiming a task is done [note and take care]
- never force-push a shared branch [important]
───────────
review the diff on feat/api and tell me what is missing
```

結尾那個字是這則的階。預設七則(`score.working-set`),整個區塊另外還有 8000 個字元的上限——超過就把排名
最低的整則丟掉,絕不會把一則截半。

線路上的每一次派送都會帶著這個區塊:直接的 `panel.dispatch`、群組扇出的每一個成員,以及排程器把佇列中的
工作排到某個面板上的那一刻。外掛發起的派送是例外——`baton.dispatch`、`baton.dispatch_group`,以及
`baton.enqueue` 排進去的工作,送出的都是原始 prompt,完全不經過 Score。

## 那個檔案

你跟 Score 之間的全部介面,就是一個你用自己的編輯器打開的純 markdown 檔。沒有接受、沒有拒絕、沒有釘選、
沒有升階——重要性是賺來的,不是給的。

```txt
- [e7f3a2] the agent was asked to gain permission it already had
- [1b90cc] run the linter before claiming a task is done
```

四條規則,而格式就只有這四條:

1. 一行一則,形狀是 `- [id] text`。id 是六個十六進位字元,由 baton 指派,並且在這則的一生中都不變——正是它
   讓「你改了這一行」這件事可以被精確回答,而不是用猜的。
2. 想編輯或刪除都可以。你的文字永遠贏過機器的。改寫某一行,舊的說法會被留下來當作別名,所以之後再出現舊
   說法的重複,依然會併進同一則。刪掉某一行,那則就退役,不管記錄檔還記得它什麼。
3. 不是一則的東西一律略過——標題、空行、你自己的散文。想在檔案裡留筆記就留;baton 會原封不動保留每一個位元組。
4. 沒有 id 的項目符號會變成一則。打 `- keep the build green`,下一次派送就會把它收成一則新的、來源是使用者
   的項目,把 id 寫回那一行,並從第 1 階開始。

第 3 條跟第 4 條合起來是唯一的陷阱。「不是一則」的意思是「不是以一個連字號加一個空格開頭的一行」。標題、
段落、`#` 註解、編號清單都是散文;markdown 的項目符號是記憶。你自己的筆記,寫成除了項目符號以外的任何
東西都好。

超過 300 個字元的一行,會照你寫的樣子完整留著,只是不會被注入——拒絕它等於改寫你的檔案,截斷它等於偷偷
改寫你的原意。`baton ctl score status` 會在 `oversized` 底下數出正在被扣住的有幾則。

Baton 只為兩件事改寫這個檔案:為一則新項目附加一行,以及把它指派的 id 寫回去。每一次寫入都是
read-reconcile-write,所以你在中間存的檔永遠不會被吃掉。

### 讓一則重新開始

刪掉某一行的 `[id]`,那則就重新開始。文字一樣,回到第 1 階,它賺到的一切都歸零:

```txt
- [e7f3a2] never force-push a shared branch     ← 第 3 階,十二次增強
- never force-push a shared branch              ← 存檔一次之後:第 1 階,什麼都沒有
```

存一次檔就完成了。那一趟會找到一則沒有任何一行帶著的活項目,把它退役;再找到一個沒有 id 的項目符號,把它
當新的收進來。舊那則的完整歷史仍然留在事件記錄檔裡——什麼都沒有被銷毀——而一個新的 id 會被寫回那一行。

這是這個 store 唯一的復原手段。沒有任何東西會自己把一則降階,所以錯爬上去的一階看起來會像是永久的,而最高
那一階是搆得到的:一份剛好重複到某則的簡報,正是最值得收回的那種升階。它由
`TestStrippingAnIdStartsAnEntryOver` 釘住——對一個讀不到程式碼的人做出的承諾,應該是一個測試,而不是一個信念。

conductor 的 `score_lower` 一次把一則往下拉一階。要一路拉回底,靠的是編輯這個檔案。

## 一則怎麼賺到它的階

| 階  | 顯示為               | 怎麼到的                                         |
| --- | -------------------- | ------------------------------------------------ |
| 1   | `noted`              | 每一則,在建立它的那次提交上                      |
| 2   | `note and take care` | 被說了 `score.promote-at` 次——預設 3 次,來源不拘 |
| 3   | `important`          | 同樣的重複,但要等到你自己說過兩次之後            |

一則觀察永遠不會被拒絕。它立刻落在第 1 階,而重要性只能靠再回來賺。不再回來的那些就待在最底下,而那不花
任何成本。

重複不會多出一行——它會併進已經這麼說的那一則,並算成一次增強。合併是比對文字的,所以兩則意思相同但說法
不同的觀察,會各自停在第 1 階,永遠爬不上去。那是刻意選的失敗方向:Score 寧可記得比較少,也不要記錯。

再多的 agent 提交都到不了第 3 階。光靠重複,會在它下面一階停住。最高那一階要的是 `score.user-signals-at`
次來自你的訊號(預設 2 次),而一個訊號是靠它進來的那條連線來辨識的,絕不是靠任何人的自稱。有三件事算是
你又說了一次:

- 在 `score.md` 裡打一行重複的(一趟只算一次訊號,不管有幾行重複帶著同一個說法——一次貼上是一個動作,
  不是五百次回來)
- 從你自己的 shell 下 `baton ctl score submit`
- 派送一份對得上既有項目的簡報——你打的 prompt 就是你在說那件事

使用者訊號抬高的是天花板,不是跳過一階。那則仍然要照一般的階梯爬上去。

修正一行的說法完全不算數。同一句話被改寫三次,還是同一句話說了一次,所以一連串的錯字修正沒辦法把一則走
到頂。

第三項有一個誠實的代價:一份剛好跟某則不相干的項目用字相同的簡報,會增強到它。每一次增強在 daemon 記錄檔
裡都有一行,寫明它算進了什麼,而修法就是上面那個——把 id 刪掉。

## 為什麼你以為會在的那則不在簡報裡

工作集是排出來的,絕不是照檔案順序取的,而且排名是一個乘積:

```txt
rank = tier × recency × cwd × profile × group
```

`tier` 是賺來的階梯——1、2、3——而且永遠不可設定。另外四個是你設的權重,各自預設 `2.0`。`cwd`、`profile`
與 `group` 在「這則是從工作目錄、agent profile 或隊伍群組等於本次派送對象的面板送出的」時值它們的權重,
不相等時值 `1.0`。`recency` 不是比對:每一則的因子在事件記錄檔中最舊位置的 `1.0` 與最新位置的權重之間
線性滑動。

接下來是值得直說的部分,因為不說的話它會被當成 bug 發現:

情境可以勝過階梯。在預設權重下,一則第 1 階、cwd/profile/group 全中的項目,分數是
`1 × 1 × 2 × 2 × 2 = 8`;而一則第 3 階、一項都沒中的,分數是 `3 × 1 × 1 × 1 × 1 = 3`。相關的小事贏過
不相關的大事——而且贏得不勉強:即使把 recency 斜坡拉到兩端,那則全中的第 1 階項目也不會低於 8,而那則
全沒中的第 3 階項目也不會高過 6。

這是設計,不是意外。選乘積而不是「先比階、再打平手」的順序,正是讓這些維度可以互相組合的原因,也是這個
旋鈕的全部用意。如果你讀到「重複賺到重要性」,然後在簡報裡找不到你的第 3 階項目,那並沒有壞掉——它只是
被某個更貼近那個面板正在做的事的東西排到後面去了。

`baton ctl score list <panel>` 會逐則列出算式,所以「這則為什麼在簡報裡」的答案是一個理由,而不是一個數字。

### 兩個面板,兩份記憶

推論下去,也是第一次讀到 Score 時最令人意外的一件事:同一支隊伍裡的兩個面板,看到的記憶真的不一樣。在一支
有七則項目的隊伍裡,派送給文件面板的那一份,跟不帶情境的 `baton ctl score list`,可以把完全不同的項目排進
前七名——一則都不重疊。

那是功能在正常運作。排序是針對簡報要落到的那個面板跑的,而一個在另一個 repository、另一個 profile、另一個
群組裡工作的面板,不會中第一個面板中的任何一項。這也表示,沒有指名面板的 `baton ctl score list` 回答的是
另一個問題:座艙不是面板,所以每一個情境因子都讀作 `1.0`,順序只由階與新近度決定。回覆會把它排序時所用的
情境一起回聲出來,所以這兩者不會被混淆。

### 那些權重

```yaml
# $HOME/.baton/config
score:
  rank:
    recency: 2.0 # 最近被碰過的那則值這麼多
    cwd: 2.0 # 從本次派送所在目錄的面板送出的項目
    profile: 2.0 # ……在本次派送的 agent profile 底下
    group: 2.0 # ……在本次派送的隊伍群組裡
```

- `1.0` 的意思是「這個維度不重要」。權重是命中時的乘數,絕不是沒中時的處罰,所以在 1.0 時,中與不中都乘 1。
  低於 1.0 的一律拉到 1.0;權重會被夾在 [1.0, 1e6] 之間,超出範圍的值會被默默修正到最近的那一端。沒設
  (或 `0`)代表「我沒設這個」,會落在預設的 2.0——它不是「關掉」的寫法。
- 四個都設成 1.0,階梯就是唯一在排序的東西。要讓賺來的重要性主導,就是這樣要求。
- 把 `cwd` 調高,目前這個 repository 就會壓過賺來的重要性。那是同一個旋鈕的另一端。
- 在 `score list` 的拆解裡讀到剛好 `1.0` 的因子,代表這個維度不是沒中就是被關掉了。`baton ctl score status`
  會回報實際生效的權重,那正是分辨這兩者的東西。

你自己從座艙送出的項目,完全不記錄面板、profile、群組或目錄,所以它們永遠不會中任何一個情境維度,只靠階
與新近度排序。

如果你正在調 `recency`,還有一個不對稱值得知道:當你編輯一則的說法時,它的位置會往前移,即使一次編輯不算
任何增強。你剛剛改過字的那一行,會排得像是很新,卻什麼都沒賺到。把 `rank.recency` 調到高過「兩則之間其他
因子的最大比值」,就是讓壓縮之後的重排變得容易發生的原因;在預設的 2.0 之下,得要有一則第 3 階的項目才可
能發生。

## 那些指令

```sh
# 記下一則關於這支隊伍怎麼做事的短觀察。
baton ctl score submit "the agent asks for permission it already has"

# store 裡的每一則,依排名順序,輸出成一行 JSON。
baton ctl score list          # 不對任何情境排——只有階與新近度
baton ctl score list 3        # 對面板 3 排:那個面板拿到的簡報

# 記憶有沒有在跑、握著幾則、怎麼調的、放在哪裡。
baton ctl score status
```

`submit` 會印出 id,而且當 store 認出這段文字是它已經握著的某則的重複時會說出來——id 仍然是第一個 token,
所以 `cut` 跟 `read` 不受影響。

`list` 是沒有上限的:每一則都在,而不是簡報帶的那幾則,每一則都附上它的階、它的排名、乘出那個排名的五個
因子,以及它的處境。它維持成一行 JSON,因為讀它的常常是 `jq` 而不是人:

```sh
baton ctl score list 3 | jq '.entries[] | select(.active)'                     # 工作集
baton ctl score list 3 | jq '.entries[] | select(.standing == "block-full")'   # 區塊裝不下的
baton ctl score list   | jq '.entries[] | select(.tier > 1)'                   # 隊伍會特別留意的
```

落在工作集之外的一則會帶著三種處境的其中一種,指名你能動手的那一個上限:

| 處境           | 意思                                       | 你的修法   |
| -------------- | ------------------------------------------ | ---------- |
| `below-budget` | 排在 `score.working-set` 之外;前面有更高的 | 把預算調寬 |
| `block-full`   | 在預算之內,但 8000 字元的區塊用完了        | 把項目寫短 |
| `oversized`    | 超過 300 字元,任何預算下都注入不了         | 編輯那一行 |

`status` 回答的是三個不同的問題,不是一個:

| 欄位                       | 說的是                                         |
| -------------------------- | ---------------------------------------------- |
| `enabled`                  | `score.enabled` 要求的是什麼                   |
| `available`                | 到底有沒有真的開起一個 store                   |
| `reason`                   | 沒開起來的話是為什麼——或者讀取或寫入已經失效了 |
| `entries` / `rendered`     | store 握著多少、一次派送會帶多少               |
| `oversized` / `block_full` | 是哪一個上限讓上面兩個數字對不起來             |
| `promote_at`、`rank`、…    | 實際生效的調校,不見得等於檔案上寫的            |
| `unlocked`                 | store 正在沒有單一寫入者宣告的情況下跑         |
| `dir`                      | 檔案在哪裡                                     |

關掉、拿不到、壞掉,是三種狀態而不是一種。你絕不應該為了知道「隊伍沒有記憶」而去讀 daemon 的記錄檔。

## conductor 的修正

在有 [conductor](CONTROL.zh-TW.md#conductor) 在跑的地方,它拿到的是修正權,不是執行權。政策——記下、合併、
計數、升階、排序、注入——是跑在 daemon 裡、用 Go 寫的決定性算術,不管有沒有 conductor 都一樣。三個 MCP
工具,對任何不是 conductor 面板的連線一律拒絕:

| 工具           | 做什麼                                             |
| -------------- | -------------------------------------------------- |
| `score_merge`  | 把兩則意思相同但說法不同的項目併起來               |
| `score_reword` | 修一則的說法;舊說法會留著,所以它的重複仍然會併進來 |
| `score_lower`  | 把錯爬上去的一則往下拉一階                         |

這三個都不算數,而且沒有任何工具可以把一則往上抬。改寫沒辦法讓一則變得更重要;被拉下來的一則,只能靠再被
說一次才爬得回去。修正的速率上限是每秒四次,而且一分鐘之內把隊伍記憶砍掉超過一半的連續合併,會在 daemon
記錄檔裡拉一個警告——因為那件事除了用手讀事件記錄檔以外沒有復原手段。

## 設定

```yaml
# $HOME/.baton/config
score:
  enabled: true # 預設值;false 會把整個子系統關掉
  dir: ~/.baton # score.md 與 score-events.jsonl 放哪裡
  promote-at: 3 # 來源不拘的出現次數,第 1 階升到第 2 階
  user-signals-at: 2 # 要幾次來自你的訊號,第 3 階才搆得到
  working-set: 7 # 一份簡報帶幾則——排名最高的那幾則
  rank:
    recency: 2.0
    cwd: 2.0
    profile: 2.0
    group: 2.0
```

每一個鍵都是選用的;沒設就是上面那個值。`promote-at` 小於 2、`working-set` 小於 1,都會被讀成沒設,而不是
把功能關掉——關掉是 `enabled` 的事。

`SIGHUP`(或 `C-t R`)會重載什麼、不會重載什麼:

| 鍵                                                                             | 會重載嗎                                |
| ------------------------------------------------------------------------------ | --------------------------------------- |
| `score.promote-at`、`score.user-signals-at`、`score.rank`、`score.working-set` | 會——每一個都是活著的 store 拿來比的數字 |
| `score.dir`、`score.enabled`                                                   | 不會——store 只在開機時開一次            |

所以,一支項目爬得太快、或簡報帶錯幾則的隊伍,用 `C-t R` 重新調校就好,不必重啟、也不必讓每一個面板都
變成已結束。搬目錄或把子系統關掉,才需要完整重啟 daemon——而當你剛重新載入的那個檔案要的是不一樣的
`score.dir` 或 `score.enabled` 時,daemon 會用 `WRN` 說出來,因為重新載入自己那一行只說了「載入過了」。
已經賺到的階是從記錄檔重放的,永遠不會動;重新調校排序改的是順序,完全不動階。

有兩個設定上的錯誤,daemon 會告訴你而不是默默吸收:鍵是 `promote-at`,還寫成 `promote_at` 的檔案會跑在
預設值上;而這一段裡任何一個打錯的數字(`working-set: lots`)會讓整個檔案解析失敗,這時原本跑著的值會
留著,而 daemon 會指名是哪個鍵。

## 把它關掉

三根拉桿,三種範圍:

```yaml
score:
  enabled: false # 整個子系統:不注入、提交被拒、檔案不動
```

檔案會留著可讀,重新打開時會從它們接續下去。這個需要重啟——store 只在開機時開一次。

```lua
-- $HOME/.baton/plug-in.lua — 針對群組、面板、任何東西,而且不需要重啟
baton.on("task.pre", function(t)
  if t.group == "scratch" then return { score = "" } end
end)
```

`task.pre` 收到的是 `{ prompt, group, score, cwd, profile, panel }`,而 `score` 是它自己的欄位,不是被前置
到 `prompt` 裡的東西——所以 hook 可以檢查它、重排它、換掉它或丟掉它,完全不必碰 prompt,而在 Score 出現
之前寫的 hook 也維持原本的意思。`C-t R` 會重載外掛,所以這根拉桿不必重啟整隊就生效。見
**[PLUGIN.md](PLUGIN.zh-TW.md)**。

第三根與其說是拉桿,不如說是「這個檔案是你的」這件事:把 `score.md` 清空,下一次派送時每一則都會退役。
(整個把檔案刪掉的效果剛好相反——不存在的檔案會被讀成遺失而不是被清空,記錄檔會被重新投影成一個新的檔案。)

## 那個目錄

`score.dir`——預設 `$HOME/.baton`,以 `0700` 建立,每個檔案 `0600`:

| 檔案                 | 裝的是                         | 誰寫的       |
| -------------------- | ------------------------------ | ------------ |
| `score.md`           | 一行一則——文字與存在與否的真相 | 你跟 baton   |
| `score-events.jsonl` | 只附加的歷史——其他一切的真相   | 只有 baton   |
| `score.lock`         | 單一寫入者的宣告               | 從來不被讀取 |

記錄檔就是真相。每一次變動都是一個事件,而所有項目在每一次開機時都是從它重建的。把記錄檔以外的檔案全刪
掉再重啟,store 會原封不動地回來。

`score.lock` 是一個在 daemon 的一生中持有的 advisory lock。兩個跑在兩個 socket 上的 daemon 預設都會用
`$HOME/.baton`,而 `BATON_SOCK` 正是官方用來跑第二支隊伍的方法——所以沒有這把鎖的話,它們會往同一個記錄檔
附加、從兩份不同的視角改寫同一個 `score.md`,而每一次改寫都會把對方的行弄丟。第二個 daemon 的 store 會直接
拒絕開啟,訊息說得很白,而且會透過 `score status` 說出來。在檔案系統根本無法上鎖的地方——企業環境裡的網路
`$HOME` 正是預設目錄會落到的地方——store 會以未上鎖的方式跑而不是拒絕開機,`status` 會回報
`unlocked: true`。兩者之中,完全沒有隊伍記憶才是比較糟的那個。

你可能會發現的一個遺留物:由較舊版本寫出來的目錄裡,還留著一個 `score.json`。這一版既不讀它也不刪它——從
你的目錄裡刪東西不是 baton 該做的事。那是死掉的位元組,你可以自己移掉。

## 壓縮,以及它的代價

每一次變動都會往 `score-events.jsonl` 附加,所以隊伍工作多久它就長多久。超過 8 MiB 之後,下一次開機會把它
改寫成「記錄檔曾經指名過的每一個 id 各一筆」:每一則活著的項目一筆狀態記錄,帶著它目前完整的狀態;每一個
項目已經不在的 id 一筆光禿禿的退役記錄。沒超過門檻就什麼都不改寫。

這是開機時的動作,而且只在開機時。一個永遠不重啟的 daemon 永遠不會壓縮,它的記錄檔會一直長到下一次啟動。
改寫是原子的——暫存檔、fsync、rename——所以任何一刻當掉,下一次開機拿到的都是一個完整的檔案可以重放;而
失敗的話,舊的記錄檔一個位元組都不會動。

它的代價,直說,不留給人自己踩到:

- 活著的東西一個都不會被銷毀,而且沒有任何一個 id 會被釋放。活著的項目會保住它的說法、別名、計數與階;
  記錄檔曾經指名過的每一個 id 都會留著一筆記錄,所以死掉那則的歷史絕不可能被接到新來的項目身上。
- 超過門檻之後,已退役項目的文字就沒了。留著它等於要在 daemon 的一生中一直握著這個 store 做過的每一次退役
  ——那正是壓縮存在要擋的成長。
- 因此,「歷史看得出這句話是哪個 agent 說的」這件事,只對還活著的項目成立。壓縮取代掉的那些動作記錄,正是
  誰在什麼時候重複了某個說法、以及哪一份簡報算成了訊號。
- 而同一條規則反過來對你有利:某個 agent 洩漏進一則、而那則後來被退役了的祕密,會從磁碟上消失。
- 新近度的間距會移動。新近度是記錄檔裡的一個位置,所以改寫記錄檔就是改寫每一個位置。順序留得住,間距留
  不住——位在 10、5000、200000 的項目回來之後變成 1、2、3。你可能會看到的,是工作集因為某個別的維度贏了
  原本由新近度決定的比較而重排。

在會造成傷害的情況下,壓縮會退讓:記錄檔在門檻以下、記錄檔解析不出任何 id、store 還欠著一次重複行的移除,
以及改寫其實不會比原本更小的時候。

Daemon 會說發生了什麼,寫在開機時的 `score recovered` 那一行:`compacted` 是寫出了幾筆記錄,`0` 代表它沒有
跑。`compaction_failures` 是改寫失敗——那不花任何資料,因為舊記錄檔完好,但它花掉的是那個上界,所以下一次
開機會比這一次慢,而再下一次又更慢。改寫失敗時還會用 `WRN` 寫出它自己的理由:光一個計數並不會告訴你磁碟
滿了。

而改寫成功時同樣會寫一行 `WRN`,因為它動了一個你沒有要求的東西——就是上面說的新近度間距。那一行會帶著
`log_before` 與 `log_after`,那是 daemon 唯一會說出記錄檔長多大的地方:記錄筆數說的是 store 記得多少,不是
裝著它的那個檔案已經長到多大。

### 回滾到舊版 binary

**被壓縮過的記錄檔,只有認得壓縮的版本讀得懂。** 這是舊版 baton 唯一不是「單純少一個新功能」的地方。

舊版不認得那些壓縮記錄,於是跳過它們,改從 `score.md` 把每一則重建回來——並且算成**你的**。在真實 store 上量
過:1400 則由 agent 提交的項目回來時全被歸給 operator,每一則的階級重置為 1,重複次數與使用者訊號全部歸零。
重新裝回新版也救不回來,因為舊版到那時候已經把那些記錄當成真相寫進記錄檔了。

掉了階級和次數,是用舊程式讀新檔案的正常代價。把 agent 說的話變成你說的話不是——那是 Score 整套設計要守住的
唯一那個分界,也是「你的一次訊號重過 agent 的一次重複」的理由。

所以:**如果回滾到舊版 `baton` 是你會做的事,在第一次會壓縮的開機之前先複製一份 `score.dir`。** `score recovered`
那一行會告訴你那是哪一次開機,而 `log_before` / `log_after` 會讓你提前知道它要來了。

## 它是什麼,不是什麼

它是一份隊伍範圍的記憶:這支隊伍一直在做的事,靠數次數學來的。

隊伍範圍會跨 repository。在某個 repo 工作時學到的一則,會被注入到在另一個 repo 工作的面板裡。情境比對會把
同一個 repo 的項目排得更前面;它不圍欄。那也就規定了一則項目應該是什麼:一句關於這支隊伍怎麼做事的話,
而絕不是一個關於某份程式碼的事實。唯一的圍欄,是你在同一個檔案裡看得到每一則。

Score 的敏感程度跟一份簡報完全一樣。它會被畫進每一個 prompt,所以裡面不該有任何 agent 本來就不會拿到的
東西。這裡沒有祕密掃描。提交會被原封不動存下來——一個提交了 token 的 agent 已經把它洩漏給整支隊伍了,而
(在那則還活著的期間)歷史看得出是哪個 agent 做的。

一則項目會到達每一個面板。一則被下毒的提交——來自被入侵或搞混的 agent——會被放大到整支隊伍。限制它的東西
有:它從第 1 階進來,顯示為 `noted`;沒有來自你的訊號,它爬不過第 2 階;而它只是一個你會編輯的檔案裡的一行。

它不是對抗惡意 agent 的邊界。一個把自己環境裡的 `BATON_PANEL_ID` 取消掉的 agent 會被蓋成你,而一個有檔案
系統存取權的 agent 可以直接寫 `score.md`。連線檢查擋掉的,是那個完全不需要任何知識的情形——宣稱一個角色,
而那是每個面板都做得到的。Shell 面板也完全拿不到身分環境,所以你在裡面手動啟動的 agent CLI,在它跑著的
期間都會被蓋成你。見 **[SECURITY.md](../SECURITY.md)**。

它不是知識庫,也不是放程式碼事實的地方。那是 `CLAUDE.md` 的工作。

它不是照時間排的。排序裡沒有任何東西讀時鐘——新近度是記錄檔裡的位置——所以一台睡了一週的筆電、一次 NTP
校正,或一次時區變更,都沒辦法重排隊伍被告知的內容。同一份記錄檔跑兩次,在任何機器上排出來的結果都一樣。
